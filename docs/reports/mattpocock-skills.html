Purpose and stance

The two layers above the problems (ADR 0010). Purpose says who the skill set is built for. Stance says where trust in the work comes from, and it follows from the purpose.

Purpose

Built for a human engineer who stays the engineer.

  • real engineering - not vibe coding README
  • You keep control: other frameworks take away your control. README
  • You keep the design in your head: glossary, ADRs, deep modules. README #2, #4
Stance my framing

Trust is built before the code.

  • Align by interview, write a spec, split into tickets.
  • Review the diff against that spec, plus coding standards.
  • You make every decision; the agent finds the facts. grilling
  • Weaker when you're away: the flow expects you at each phase. inferred

How you would use it

Start from your situation. Each box is what you type, and the label on each arrow is what you'd say or decide at that point. Grey boxes are skills the agent reaches for by itself.

flowchart TD
  start([New repo]) --> setup["/setup-matt-pocock-skills (once)"]
  setup --> q{What do you have?}
  q -->|an idea to build| grill["/grill-with-docs"]
  q -->|a bug that resists a first look| bug[diagnosing-bugs]
  q -->|issues you didn't write| tri["/triage"]
  q -->|a huge, foggy effort| way["/wayfinder"]
  q -->|a spare moment| ica["/improve-codebase-architecture"]
  q -->|not sure| ask["/ask-matt"]
  ask -.->|recommends one| q
  ica -->|pick a candidate| grill
  grill --> ans{Can every question be settled by talking?}
  ans -->|no, need to see it| proto["/handoff → prototype → /handoff"]
  proto --> grill
  ans -->|yes| size{Fits in one session?}
  size -->|yes| impl["/implement here"]
  size -->|no| spec["/to-spec → /to-tickets"]
  way -->|map is clear| spec
  spec --> how{Drive each ticket yourself?}
  how -->|yes| per["/implement per ticket, /clear between"]
  how -->|no, orchestrate| all["/implement-spec"]
  tri -->|agent-ready issue| impl
  impl --> auto[tdd → code-review → pr]
  per --> auto
  all --> auto
  bug -->|fixed + regression test| retro
  auto --> retro["/retro before you /clear"]
  retro -->|better checks and standards| q

Positions that only work together

If you adopt one side of a pair in Phase 2, check the other side too.

  • 1·3·6

    You as decider, heavy planning and spec/ticket artifacts are one package. Drop to-spec/to-tickets and multi-session builds have no input.

  • 6·10

    Clearing context between tickets only works because each ticket is self-contained.

  • 3·8

    code-review's Spec check needs a spec; without one it skips.

  • 4·11

    inferred wait-what and the short vocabulary need the glossary that grill-with-docs builds.

  • 2·14·15

    The user-invoked / model-invoked split keeps process skills apart from reference skills.

  • 13·6

    Setup runs first; triage, spec, tickets and review read its tracker config.

  • 7·8

    Refactoring moves out of TDD into review; the reviewer enforces standards because it has less context pressure.
