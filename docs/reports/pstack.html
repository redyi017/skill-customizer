Purpose and stance

The two layers above the problems (ADR 0010). Purpose says who the skill set is built for. Stance says where trust in the work comes from, and it follows from the purpose.

Purpose

Built for an operator who delegates as much as possible.

  • stop micromanaging the agent guide
  • fearless parallelism: many agents at once. README
  • You keep goals and judgment calls: Product direction comes from the human. Execution should not block. never-block-on-the-human
Stance my framing

Trust is built after the code, by independent proof.

  • The writer is never the judge: a fresh agent verifies each PR live.
  • Different model families review the same work.
  • Every claim is labeled measured, inferred or guess. poteto-mode
  • Weaker on "is this the right feature": no spec to review against, and the design checkpoint is off by default. inferred

How you would use it

You type one prompt to /poteto-mode with a goal and a way to check it. The words you use pick the playbook. Dashed boxes are skills you can also type yourself when you want more or less than the playbook gives.

How the pieces connect

A router, not a pipeline. Each playbook calls the skills it needs, and they call each other.

flowchart LR
  mode[poteto-mode] -->|reads| pr[24 principles]
  mode --> pb[playbook steps in todo list]
  pb --> how[how] & why[why]
  pb --> arch[architect] --> arena[arena]
  arch --> how
  pb --> del[poteto-agent delegate] -->|diff| ver[verify on real surface]
  ver --> clean[deslop, no-comments, unslop]
  clean --> inter[interrogate: other models try to break it]
  inter --> open[Opening a PR]
  teach[teach] --> how
  teach --> why

When you're offline

pstack plans for you being away. You leave a short contract, it loops without relaxing the goal, and you audit a log when you're back.

flowchart LR
  t["Trust check:
done it once, agent has your tools"] --> k["Contract:
goal, pass/fail done check,
worktree, escape hatch"]
  k --> l["/loop: check the goal"] --> c[one change] --> v[verify on the real app]
  v -->|progress| cm[commit] --> lg[log one row]
  v -->|no progress| dc[discard] --> lg
  lg --> l
  v -.->|can't undo, or your call| park[pause, or default + report]
  lg -.->|goal met or dead end| a["Back: Attention list
from another model"]

Context stays small because the main chat works from subagent summaries and keeps its state in files. In Claude Code, cloud agents become local worktrees, so your machine has to stay on inferred, untested.

Where you step in

  • default

    Reversible work goes ahead without asking. You correct it afterward.

  • always

    Irreversible actions pause: force-push, deploys, data deletion, customer messages.

  • decide

    Product or preference calls that no prototype can settle.

  • opt in

    "/architect with checkpoint" or "let me review before proceeding".

  • approve

    reflect's skill edits, a plan's go, and any merge. Babysit stops at merge-ready.

  • audit

    The decision log, with an Attention section written by a reviewer on another model.

Positions that only work together

  • 1·4·10

    Not blocking on you only works because the prompt has a pass/fail check and the decision log replaces live supervision.

  • 9·13·15

    Multi-model review needs the role-to-model mapping from setup.

  • 3·8

    inferred No planning step works because prototypes and live verification do a spec's job.

  • 7·12

    correct ranks fixes by enforcement: architecture, types, lint, test, docs last.

  • 6·9

    Parallel workers each need their own worktree or cloud agent.

  • 8·9

    The agent that judges a change is never the one that wrote it, so verification needs subagents.
